| `CONN-POSTIZ-AGENT-R010` | **Post lifecycle is one explicit state machine (rollup).** A Postiz post is in exactly one of six states: Draft, Queued, Publishing, Published, Error, Deleted. Deleted is the only terminal state. Intent (what the caller asks) and observed state (what the server reports) are separate vocabularies that the machine joins. Postiz keeps a connector-side `publishing` state. The server never reports it. The connector enters it when the server accepts a publish-now call. It leaves it when a read reports PUBLISHED (Succeed), a read reports ERROR (Fail), or a release id is recorded (RecordRelease). The stored field is the server `state` (`postiz_agent/postiz_models.py:68`). `lifecycleState` is derived from it. One transition function decides every move and refuses an illegal move with a typed error before the server call. Tools stay one per API operation. The single transition function is `postiz_agent/lifecycle.py::post_transition`, owned by this repository. Children `.1` to `.7`. Depends on: SCION-GOVERNED-WRITEBACK-R007, SCION-CONNECTOR-CONTROL-R917 and MEDULLA-ORCH-VOCAB-R811. Rule: constitution Article XXXI. | Rollup closes when `.1` to `.7` are verified. Root test: `tests/test_post_lifecycle.py::test_served_tools_refuse_illegal_moves_with_zero_write_requests`. |
| `CONN-POSTIZ-AGENT-R010.1` | **Declare the post machine and its transition function.** `postiz_agent/lifecycle.py` (new) declares `PostState` (Draft, Queued, Publishing, Published, Error, Deleted) and `PostEvent` (Schedule, PublishNow, Unschedule, Edit, Succeed, Fail, Retry, RecordRelease, Delete). Legal moves: Draft+Schedule to Queued, Draft+PublishNow to Publishing, Queued+Unschedule to Draft, Queued+PublishNow to Publishing, Publishing+Succeed to Published, Publishing+Fail to Error, Error+Retry to Queued, Draft+Edit to Draft, Queued+Edit to Queued, Publishing+RecordRelease to Published, Draft+Delete, Queued+Delete, Error+Delete and Published+Delete to Deleted. Deleted is terminal. Every other pair is refused. `post_transition(state, event)` returns the next state or raises the typed `IllegalTransition`, defined in `postiz_agent/lifecycle.py`. It carries the fields machine (`PostLifecycle`), post id, from-state, event and reason. The connector-side `publishing` state is persisted as data (constitution Article XXXI), never held in memory only: `PublishingStore` in `postiz_agent/lifecycle.py` keeps the post ids in a SQLite file (`POSTIZ_LIFECYCLE_STORE`, on a persistent volume in the cluster), because the public Postiz API cannot add a tag or customer field to an existing post. `PublishNow` enters it only after a successful server response. A process restart keeps it; it leaves on Succeed, Fail or RecordRelease. Caller chain: the guarded post operations of R010.3 call `post_transition`. Shape: pure enums and one closed table; no I/O. Depends on: none. Sizing: one five-minute row. | Every legal pair reaches its state and every other pair raises `IllegalTransition`. One parametrised test covers the table, with ids `draft-schedule`, `draft-publishnow`, `queued-unschedule`, `queued-publishnow`, `publishing-succeed`, `publishing-fail`, `error-retry`, `draft-edit`, `queued-edit`, `publishing-recordrelease`, `draft-delete`, `queued-delete`, `error-delete` and `published-delete`: `tests/test_post_lifecycle.py::test_every_legal_transition_reaches_its_state[<id>]`. Refusal: `tests/test_post_lifecycle.py::test_every_other_pair_is_refused_with_a_typed_error`. Fields: `tests/test_post_lifecycle.py::test_illegal_transition_carries_machine_from_state_and_event`. Publishing: `tests/test_post_lifecycle.py::test_publishing_is_entered_on_accepted_publish_now_and_left_on_succeed_fail_or_release`. |
| `CONN-POSTIZ-AGENT-R010.2` | **Separate intent from observed state and map the server vocabulary once.** `postiz_agent/lifecycle.py` declares `intent_event(create_type)`, which maps the create `type` (`draft`, `schedule`, `now`) in `PostizCreatePostRequest` (`postiz_agent/postiz_models.py:47`) to the event the caller asks for, and `state_of(post)`, which maps the server `state` (`DRAFT`, `QUEUE`, `PUBLISHED`, `ERROR`, `postiz_agent/postiz_models.py:68`) to `PostState`. | `CONN-POSTIZ-AGENT-R010.3` | **Guard update, status change, retry and delete before the server call.** The existing tools `postiz_update_post_settings` (`postiz_agent/api/api_client_posts.py:132`), `postiz_change_post_status` (`:147`), `postiz_update_release_id` (`:119`), `postiz_delete_post` (`:88`) and `postiz_delete_post_by_group` (`:98`) read the post, derive its state and call `post_transition` before the write. Update is allowed only in Draft or Queued. A status change to draft is the Unschedule event and needs Queued; a retry is the Retry event and needs Error. Delete of a Published post is legal and its result says the record is removed and the provider post is untouched (unlist only). Every other state refuses with the reason code. For a group delete the guard runs per post and refuses the whole call if any post refuses. Caller chain: the served tools call these methods; `postiz_agent/api_client.py` applies the guard by operation name. Shape: one `guarded(operation, event)` wrapper, so the one-tool-per-operation surface of `CONN-POSTIZ-AGENT-R003` is unchanged. Depends on: `CONN-POSTIZ-AGENT-R010.2`. Sizing: one five-minute row. | A refused call makes no write request. Tests: `tests/test_post_lifecycle.py::test_update_is_refused_outside_draft_and_queued_without_a_write`, `tests/test_post_lifecycle.py::test_retry_needs_error_and_delete_of_published_is_unlist_only` (transitions Error+Retry and Published+Delete), `tests/test_tool_surface.py::test_every_upstream_operation_is_one_typed_tool`. |
