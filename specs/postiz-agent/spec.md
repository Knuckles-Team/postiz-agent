# CONN-POSTIZ-AGENT — Postiz connector

## Outcome

The connector must reach the Postiz public API at the path the server actually serves, document the deployment prerequisite the server needs to answer, and serve every Postiz operation as a typed tool with the prompt, skills and ontology a business needs to schedule campaign posts from its assets.

## Scope and owner

The `postiz-agent` repository owns Postiz operations and their source mappings.
The shared connector SDK owns reusable transport, authentication, and MCP contracts.

Component: Connector integration
Code: ../../postiz_agent/api/ ../../postiz_agent/ontology/ ../../postiz_agent/prompts/ ../../postiz_agent/skills/ ../../tests/

## Non-goals

This specification grants no service access, credential creation, or deployment approval.

## User Scenarios & Testing

### User Story 1 - API base path (Priority: P1)

The fleet operator and the engine rely on this behaviour of `postiz-agent`: The client must build every request URL under `<host>/api/public/v1` in `postiz_agent/api/api_client_base.py`, because the server answers `/public/v1` with a 307. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_coverage_gap_fillers.py::test_api_client_url_normalization` runs, **Then** `tests/test_coverage_gap_fillers.py::test_api_client_url_normalization` must observe the normalized base without network access.

### User Story 2 - Workflow engine prerequisite (Priority: P1)

The fleet operator and the engine rely on this behaviour of `postiz-agent`: A self-hosted Postiz deployment must provide a Temporal service and set `TEMPORAL_ADDRESS`, otherwise the backend exits and `/api/*` returns 502. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_postiz_temporal_prerequisite.py::test_acceptance_call_returns_non_502` runs, **Then** the deployment manifest in the services repository must declare the `temporal` service; the connector acceptance call must return a non-502 response.

### User Story 3 - Typed operation surface (Priority: P1)

The business's social media workflow relies on this behaviour of `postiz-agent`: Every operation of the Postiz public API (the v1 controller and the preview routes) must be served as its own typed MCP tool with a documented description, generated by the SDK tool surface from one documented method of `PostizApi`. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_tool_surface.py::test_every_upstream_operation_is_one_typed_tool` runs, **Then** every upstream operation maps to a served tool with no `action` or `params_json` input, and delete tools are destructive.

### User Story 4 - Media upload from bytes (Priority: P1)

The business's social media workflow relies on this behaviour of `postiz-agent`: `postiz_upload_file_content` must upload base64 media bytes (an image or a short video) to `POST /upload` as multipart with the MIME type from the file name, so a remote caller can move an asset from another system. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_tool_surface.py::test_upload_file_content_posts_multipart_bytes` runs, **Then** the upload posts the exact bytes with the guessed MIME type and no JSON content type; bad payloads make no request.

### User Story 5 - Draft-first posting, status change and cancel (Priority: P1)

The business's social media workflow relies on this behaviour of `postiz-agent`: `postiz_create_post` must default `type` to `draft`, accept only `draft`, `schedule` or `now`, and require at least one post. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_tool_surface.py::test_create_post_defaults_to_draft` runs, **Then** a request without a type is a draft; an unknown type or an empty post list is refused; status and delete return the JSON body.

### User Story 6 - Preview and review comments (Priority: P1)

The business's social media workflow relies on this behaviour of `postiz-agent`: `postiz_get_post_preview`, `postiz_list_post_comments` and `postiz_create_post_comment` must call the unauthenticated preview routes under `<host>/api/public/posts/{id}` (one level above the v1 base), so a post can be reviewed before it is scheduled. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_tool_surface.py::test_preview_and_comments_use_the_public_root` runs, **Then** preview and comment calls hit `/api/public/posts/...` with the documented body.

### User Story 7 - Social media manager prompt and campaign skill (Priority: P1)

The business's social media workflow relies on this behaviour of `postiz-agent`: The package must serve the `social_media_manager` prompt and the `postiz-campaign-post-from-asset` skill (asset to draft, preview, schedule, verify, cancel, analytics), and every tool the skill names must be a served tool. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_tool_surface.py::test_prompt_and_campaign_skill_are_served` runs, **Then** the prompt is listed and every tool named by the skill is served.

### User Story 8 - Ontology pack: surface, data location and core roll-up (Priority: P1)

The business's social media workflow relies on this behaviour of `postiz-agent`: `postiz_agent/ontology/pack.ttl` must declare the connector, its features, one `cp:Tool` per served tool with its `cp:operatesOn` domain class, the prompt and the skills, the ingest contract, and one `vg:SourceAuthority` per domain class saying the Postiz source is the live truth and whether medulla keeps an accelerated copy. Every domain class of `social.ttl` must reach a core class by `rdfs:subClassOf`, and no ontology file uses `owl:imports`. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_pack_surface.py::test_pack_declares_every_served_tool_prompt_and_skill` runs, **Then** the declared tools, prompts and skills equal the served ones, and every domain class rolls up to a core class without an import.

### User Story 9 - Declared ingest sources and mapping pins (Priority: P1)

The business's social media workflow relies on this behaviour of `postiz-agent`: `postiz_agent/connector_sources.py` must declare the posts, channels, media and notifications read tools as ingest sources, and `ontology/mappings/source.yaml` must name those typed tools (no `action`) with the compatibility pin of their live schema. It is proven independently of the other stories.

**Acceptance Scenarios**:

1. **Given** the `postiz-agent` connector built from the default branch, **When** `tests/test_pack_surface.py::test_declared_sources_and_mapping_pins_match_the_live_tools` runs, **Then** the served sources are exactly the four declared tools and every pin equals the live tool's compatibility digest.

### Edge Cases

- The vendor service is unreachable or rejects the credential: the connector returns the SDK typed error and never a partial result.
- An argument outside the documented inputs is refused with the SDK typed refusal and causes no effect on the vendor service.
