# CONN-POSTIZ-AGENT — Requirements

Governing specification: [spec.md](spec.md).

| ID | Requirement | Acceptance |
|---|---|---|
| `CONN-POSTIZ-AGENT-R001` | **API base path.** The client must build every request URL under `<host>/api/public/v1` in `postiz_agent/api/api_client_base.py`, because the server answers `/public/v1` with a 307. An explicit base containing `/public/v1` is kept unchanged. Caller chain: an MCP tool of `postiz_agent/mcp_server.py` calls a domain client, which builds every URL from the base normalised at `postiz_agent/api/api_client_base.py:15`. Shape: the base-path normalisation in `postiz_agent/api/api_client_base.py`; an explicit base that contains `/public/v1` is kept. Proving test: `tests/test_coverage_gap_fillers.py::test_api_client_url_normalization`. | `tests/test_coverage_gap_fillers.py::test_api_client_url_normalization` must observe the normalized base without network access. |
| `CONN-POSTIZ-AGENT-R002` | **Workflow engine prerequisite.** A self-hosted Postiz deployment must provide a Temporal service and set `TEMPORAL_ADDRESS`, otherwise the backend exits and `/api/*` returns 502. Caller chain: the Postiz backend process of a self-hosted deployment starts its workflow worker, which connects to the address in `TEMPORAL_ADDRESS`; every connector call to `/api/*` passes through that backend. Shape: the deployment manifest of the Postiz stack in the services repository declares the `temporal` service and sets `TEMPORAL_ADDRESS`; the connector adds no code. Proving test (planned): `tests/test_postiz_temporal_prerequisite.py::test_acceptance_call_returns_non_502`. Proving test (planned): `tests/test_postiz_temporal_prerequisite.py::test_acceptance_call_returns_non_502`. Proving test (planned): `tests/test_postiz_temporal_prerequisite.py::test_acceptance_call_returns_non_502`. | The deployment manifest in the services repository must declare the `temporal` service; the connector acceptance call must return a non-502 response. |
| `CONN-POSTIZ-AGENT-R003` | **Typed operation surface.** Every operation of the Postiz public API (the v1 controller and the preview routes) must be served as its own typed MCP tool with a documented description, generated by the SDK tool surface from one documented method of `PostizApi`; no tool routes an `action` string or takes a `params_json` blob, and delete operations carry the destructive annotation. Caller chain: an MCP client lists the `postiz-mcp` tools; `scion_sdk.connector.build_server` registers one tool per public method of `postiz_agent/api_client.py::PostizApi`. Shape: `postiz_agent/api/*.py` (one method per operation), `postiz_agent/mcp_server.py` (ingest tools only). Proving test: `tests/test_tool_surface.py::test_every_upstream_operation_is_one_typed_tool`. | Every upstream operation maps to a served tool with no `action` or `params_json` input, and delete tools are destructive. |
| `CONN-POSTIZ-AGENT-R004` | **Media upload from bytes.** `postiz_upload_file_content` must upload base64 media bytes (an image or a short video) to `POST /upload` as multipart with the MIME type from the file name, so a remote caller can move an asset from another system; Postiz refuses private-network URLs for `upload-from-url`. Invalid or empty base64 and payloads over 50 MiB are refused before any request. Caller chain: the `postiz_upload_file_content` tool calls `UploadsClient.postiz_upload_file_content` in `postiz_agent/api/api_client_uploads.py`, which posts the decoded bytes. Shape: `postiz_agent/api/api_client_uploads.py`. Proving test: `tests/test_tool_surface.py::test_upload_file_content_posts_multipart_bytes`. | The upload posts the exact bytes with the guessed MIME type and no JSON content type; bad payloads make no request. |
| `CONN-POSTIZ-AGENT-R005` | **Draft-first posting, status change and cancel.** `postiz_create_post` must default `type` to `draft`, accept only `draft`, `schedule` or `now`, and require at least one post; `postiz_change_post_status` moves a post between `draft` and `schedule`; delete and status tools return the server's JSON whatever its value types (a boolean result no longer fails the call). Caller chain: the `postiz_create_post`, `postiz_change_post_status` and `postiz_delete_post` tools call `PostsClient` in `postiz_agent/api/api_client_posts.py`; the request model is `postiz_agent/postiz_models.py::PostizCreatePostRequest`. Shape: `postiz_agent/api/api_client_posts.py`, `postiz_agent/postiz_models.py`. Proving test: `tests/test_tool_surface.py::test_create_post_defaults_to_draft`. | A request without a type is a draft; an unknown type or an empty post list is refused; status and delete return the JSON body. |
| `CONN-POSTIZ-AGENT-R006` | **Preview and review comments.** `postiz_get_post_preview`, `postiz_list_post_comments` and `postiz_create_post_comment` must call the unauthenticated preview routes under `<host>/api/public/posts/{id}` (one level above the v1 base), so a post can be reviewed before it is scheduled. Caller chain: the preview tools call `PreviewClient` in `postiz_agent/api/api_client_posts.py`, which uses `preview_url` derived in `postiz_agent/api/api_client_base.py`. Shape: `postiz_agent/api/api_client_base.py`, `postiz_agent/api/api_client_posts.py`. Proving test: `tests/test_tool_surface.py::test_preview_and_comments_use_the_public_root`. | Preview and comment calls hit `/api/public/posts/...` with the documented body. |
| `CONN-POSTIZ-AGENT-R007` | **Social media manager prompt and campaign skill.** The package must serve the `social_media_manager` prompt and the `postiz-campaign-post-from-asset` skill (asset to draft, preview, schedule, verify, cancel, analytics), and every tool the skill names must be a served tool. Caller chain: `scion_sdk.mcp.content` serves `postiz_agent/prompts/*.json` as MCP prompts and `postiz_agent/skills/*/SKILL.md` as `skill://` resources when the server is built. Shape: `postiz_agent/prompts/social_media_manager.json`, `postiz_agent/skills/postiz-campaign-post-from-asset/`. Proving test: `tests/test_tool_surface.py::test_prompt_and_campaign_skill_are_served`. | The prompt is listed and every tool named by the skill is served. |
| `CONN-POSTIZ-AGENT-R008` | **Ontology pack: surface, data location and core roll-up.** `postiz_agent/ontology/pack.ttl` must declare the connector, its features, one `cp:Tool` per served tool with its `cp:operatesOn` domain class, the prompt and the skills, the ingest contract, and one `vg:SourceAuthority` per domain class saying the Postiz source is the live truth and whether medulla keeps an accelerated copy. Every domain class of `social.ttl` must reach a core class by `rdfs:subClassOf`, and no ontology file uses `owl:imports`. Caller chain: the SDK serves `postiz_agent/ontology/*.ttl` as `ontology://postiz-mcp/<file>` resources, which medulla federates. Shape: `postiz_agent/ontology/pack.ttl`, `postiz_agent/ontology/social.ttl`. Proving test: `tests/test_pack_surface.py::test_pack_declares_every_served_tool_prompt_and_skill`. | The declared tools, prompts and skills equal the served ones, and every domain class rolls up to a core class without an import. |
| `CONN-POSTIZ-AGENT-R009` | **Declared ingest sources and mapping pins.** `postiz_agent/connector_sources.py` must declare the posts, channels, media and notifications read tools as ingest sources, and `ontology/mappings/source.yaml` must name those typed tools (no `action`) with the compatibility pin of their live schema. Caller chain: the SDK serves the declaration as `connector://resources`; the ingest runner validates each preset's pin against the live tool. Shape: `postiz_agent/connector_sources.py`, `postiz_agent/ontology/mappings/source.yaml`. Proving test: `tests/test_pack_surface.py::test_declared_sources_and_mapping_pins_match_the_live_tools`. | The served sources are exactly the four declared tools and every pin equals the live tool's compatibility digest. |
